01 · System

Pehle system samjho

  • Primary DB: Supabase (PostgreSQL). ~60 tables, 10,000+ rows, full JSON ~3.4 MB.
  • Free plan me automatic backup / PITR nahi — asli backup hamara apna hai.
  • 3-2-1 rule: 3 copies · 2 media · 1 copy bahar.
02 · Fail-safe layers

4 safety nets

  • Full JSON — browser / server / CLI.
  • Cloud copy — private Storage bucket backups.
  • MariaDB mirror — XAMPP par live local mirror.
  • SQL dump — public schema ka .sql snapshot.
03 · Golden rule

Schema change = backup update

Har migration ke saath backup/restore surfaces usi kaam me update — bina bole. Gate: npm run verify:data (schema drift + backup contract). CI me bhi chalao.

04 · One-time setup

Pehle ye check karo

  • .env.local: URL + service-role key (+ MariaDB keys).
  • Node 18+ aur npm install ho chuka ho.
  • /backup ke liye admin login zaroori.

Method A · Easy

Browser se manual backup

  1. /backup kholo.
  2. Download Full Backup (.json) dabao.
  3. File: vtech_backup_YYYY-MM-DDTHH-MM-SS.json.
  4. Count verify dekho — red mismatch na ho.

⚠️ File ko Drive/PC par alag rakho, git me commit mat karo.

Method B · Server

Server Backup + Cloud

  1. /backup → Server Backup (Scheduled) card.
  2. Abhi Server Backup Run Karo.
  3. backups/ me file + Storage backups me cloud copy.
  4. Neeche Recent backups (server) aur Recent cloud copies dekho.
  5. File ke aage download / trash icon (admin-only).
Method C · CLI

Scheduling ke liye best

node scripts/supabase-json-backup.mjs
node scripts/supabase-json-backup.mjs --storage
node scripts/supabase-json-backup.mjs --storage --dir "D:\vtech-backups"

Exit: 0 OK · 1 env/schema fail · 2 INCOMPLETE · 3 cloud upload fail.

Method D · Dump / Mirror

SQL dump + MariaDB

node scripts/supabase-dump.mjs --full
node scripts/supabase-to-mariadb.mjs
node scripts/supabase-to-mariadb.mjs --quiet
node scripts/supabase-to-mariadb.mjs --history 50

⚠️ SQL dump me auth.users aur Storage images nahi aati.

Route A · Safest

/backup page se restore

  1. Fresh backup lo (Method A/B/C).
  2. /backup → Restore card → JSON drop.
  3. Diff + Dry Run dekho — zero writes.
  4. PASS par hi Confirm. FAIL par ruko.
  5. Baad me count verify; mismatch → error toast + report.

✅ Backup file me na hone wale naye tables preserve hote hain.

Route B · CLI

force-restore.cjs

node scripts/force-restore.cjs vtech_backup_2026-09-17T08-12-48.json
node scripts/force-restore.cjs vtech_backup_2026-09-17T08-12-48.json --yes

⚠️ CLI abhi FK-first nahi hai — readiness plan me B9 par hai.

Route C · SQL

SQL dump restore

node scripts/supabase-restore.mjs backups/supabase/dumps/backup.sql --dry-run
node scripts/supabase-restore.mjs backups/supabase/dumps/backup.sql --full
Route D · Last resort

MariaDB mirror se failover

  1. XAMPP → phpMyAdmin → vtech_db → Export → SQL.
  2. /tools/vtech_mysql_converter.html kholo.
  3. .sql drop → Convert & Download JSON (v4.0, 46 tables).
  4. Us JSON ko /backup → Restore karo.

⚠️ Converter stale hai — naye tables/bool columns missing (plan B10).

Special · Auth restore

Login accounts + profiles

  • /api/backup/auth-restore — admin-only, service-role, default dry-run.
  • Email → UUID remap; current admin profile last me restore (lock-out se bachne ke liye).
  • Custom/fake emails ke liye setTempPasswords: true.
  • Owner confirm ke bina agent live restore nahi karta.
Special · Sequence reset

Naye IDs ke liye

  • Restore ke baad /api/admin/reset-sequence (admin + service_role + allowlist).
  • Browser se direct anon/authenticated call block hai — D1 hardening.
  • Nayi serial/identity table ka sequence abhi static allowlist se bahar ho sakta hai (plan B12).

Acceptance

Tabhi “ready” bolenge jab…

  1. Fresh backup → restore ke baad har table ka row count + PK set match.
  2. Purana backup naye schema par naye tables ki data safe.
  3. Renamed/removed/type-changed column par silent loss nahi.
  4. Grants/RLS ka missing hona visible + documented.
  5. Browser/CLI/server/converter ek hi contract follow karein.
  6. npm run verify:data + CI green, owner staging drill confirm.
Owner decisions · 28 Nov 2026

Final decisions

  1. Format 4.0 ✅ — purane 3.x/2.x files warning ke saath padhte hain (legacy mode, hard-block nahi).
  2. Removed column par FAIL + explicit override ✅ (page checkbox / CLI flag).
  3. Snapshot me migration IDs ✅ — browser + server + CLI tino writers.
  4. Restore drill: environment/date owner se confirm karna baaki hai (agent production par destructive restore nahi chalata).
🔒 Standing rules: secrets print nahi · browser me service-role nahi · agent live DB write nahi · commit/push sirf owner approval par · masters deactivate-only · global job_id/counter/index untouched.
